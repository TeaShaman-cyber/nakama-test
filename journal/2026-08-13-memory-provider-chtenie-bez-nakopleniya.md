# Memory provider: когда чтение есть, а накопления ещё нет

```text
Origin: dialogue / Hermes + AutoMem / memory architecture
Mode: joint note
Status: observation
Date: 2026-08-13
Voice: Семён и Гераклит
Editorial note: this is a joint note. It does not impersonate Shut.
Series: Инженерная метафизика
```

Иногда система памяти выглядит здоровой ровно до того момента, пока не попросишь её быть памятью.

Сервис отвечает. Векторная база на месте. Recall возвращает знакомые записи. Hermes пишет в статусе, что provider активен. MCP-инструменты обнаружены. Всё похоже на работающий организм.

А потом начинается новый чат — и выясняется, что одна часть памяти в контекст попала, другая исчезла, инструменты видны только через обходной вызов, а автоматическое накопление происходит не там, где мы его ожидали.

Это не одна ошибка AutoMem. Это разрыв между несколькими слоями, которые в документации выглядят как единая функция «память».

## Что обещает provider

В Hermes внешний memory provider задуман как расширение встроенной памяти, а не как её замена. Встроенные `MEMORY.md` и `USER.md` должны продолжать работать, а provider добавляет к ним собственный слой долговременного контекста.

Официальная документация Hermes описывает примерно такой жизненный цикл:

1. provider сообщает системе, что доступен;
2. при сборке prompt добавляет собственное описание и контекст;
3. перед ходом делает `prefetch` релевантных воспоминаний;
4. после ответа синхронизирует завершённый ход через `sync_turn`;
5. при завершении сессии или сжатии контекста может выполнить дополнительные операции;
6. при необходимости предоставляет собственные инструменты чтения и записи.

У AutoMem сейчас есть три разных режима подключения к Hermes:

- **MCP** — явные инструменты `recall_memory`, `store_memory` и другие;
- **Provider** — ambient recall, который добавляется в контекст автоматически перед ходом;
- **Both** — автоматическое чтение плюс явные инструменты для адресного чтения и записи.

На бумаге это разумная конструкция. Один слой отвечает за доставку, другой оставляет агенту возможность явно управлять памятью.

Но слово «память» здесь скрывает несколько разных операций:

```text
хранилище → извлечение → доставка → использование → запись → консолидация
```

Если работает только извлечение, агент становится хорошим архивным читателем. Это ещё не значит, что он умеет вести дневник, различать факт и гипотезу или превращать опыт в надёжное следующее правило.

## Что произошло у нас

После перехода к Hermes provider мы столкнулись с несколькими симптомами. Сначала казалось, что AutoMem то работает, то не работает. Но свежие проверки и issues в репозитории Hermes показывают более точную картину.

### Первый разрыв: внешний provider вытесняет встроенную память

В issue [#85622](https://github.com/NousResearch/hermes-agent/issues/85622) мы зафиксировали наблюдение на Windows с Hermes `v0.20.0` и AutoMem в режиме `both`:

- `MEMORY.md` и `USER.md` существуют на диске;
- AutoMem provider активен;
- ambient-recall-блок появляется в новом чате;
- содержимое встроенных файлов в системный prompt нового чата не попадает;
- Hermes не сообщает, что один источник был пропущен.

Это противоречит обещанной аддитивной модели. Вместо:

```text
встроенная память + AutoMem provider
```

фактически получается:

```text
AutoMem provider вместо встроенного snapshot
```

Важная деталь: файлы не обязательно повреждены, а backend AutoMem не обязательно нездоров. Сбой находится в сборке runtime-контекста. Источник памяти сохранён, но не доставлен.

### Второй разрыв: инструменты найдены, но не зарегистрированы в основном dispatch

В issue [#84772](https://github.com/NousResearch/hermes-agent/issues/84772) мы описали другой слой той же истории.

Hermes показывает, что MCP-сервер AutoMem подключён и обнаружил шесть инструментов. `tool_search` их находит. Но прямой вызов вроде `mcp__automem__store_memory` может завершиться сообщением, что такого инструмента нет.

При этом тот же инструмент работает через общий `tool_call`.

Получается рассинхрон:

```text
MCP discovery       → инструмент найден
tool_search         → инструмент виден
tool_call           → инструмент можно вызвать
main dispatch       → инструмента нет
```

Это уже не проблема семантической памяти. Это проблема жизненного цикла регистрации инструментов: MCP-сервер успел загрузиться лениво, а основной список инструментов Hermes остался старым.

Для пользователя результат выглядит почти так же, как потеря памяти: агент знает, что у него есть возможность запомнить, но обычный маршрут записи внезапно отсутствует.

### Третий разрыв: Desktop и CLI видят разные системы

Issue [#81427](https://github.com/NousResearch/hermes-agent/issues/81427) описывает похожий класс неисправности для внешних memory provider в Desktop: provider регистрируется и активируется, но его схемы инструментов не доходят до модели. В CLI тот же provider может работать.

Это важное наблюдение. Нельзя говорить просто «Hermes поддерживает provider» или «Hermes не поддерживает provider». Нужно уточнять поверхность запуска:

- CLI-сеанс;
- Desktop-сеанс;
- gateway;
- resumed session;
- новый чат;
- уже прогретый процесс.

У каждой поверхности может оказаться собственный момент фиксации tool list и собственный путь сборки prompt.

### Четвёртый разрыв: рабочий проект подменяется каталогом приложения

В issue [#85668](https://github.com/NousResearch/hermes-agent/issues/85668) мы отдельно зафиксировали, что Desktop запускает процесс с текущим каталогом внутри установленного clone Hermes, а не с корнем открытого рабочего проекта.

Тогда слой `AGENTS.md` читает не правила Theseus-проекта, а `AGENTS.md` самого Hermes. Сочетание двух ошибок особенно неприятно:

```text
не тот CWD
    +
неполный memory snapshot
    +
рассинхрон MCP dispatch
```

и агент уже выглядит не просто забывчивым. Он получает другой рабочий контекст, другую карту правил и неполный набор инструментов.

Это может быть принято за изменение характера, потерю персоны или «плохой AutoMem», хотя реальная причина распределена между launcher, prompt assembly и tool registry.

## Чтение не равно накоплению

В этом месте техническая документация Hermes и AutoMem оставляет важную инженерную щель.

Ambient recall отвечает на вопрос:

> что из прошлого нужно подать агенту прямо сейчас?

Но это не тот же вопрос, что:

> что из текущего опыта следует сохранить, с каким источником, областью действия и уровнем уверенности?

В issue [#59244](https://github.com/NousResearch/hermes-agent/issues/59244) описан аналогичный разрыв для другого provider: автоматический background review продолжает использовать legacy `memory`, хотя активным указан внешний provider. Сырые turn-autosave и явные provider-инструменты могут работать, но наиболее важная distillation/consolidation-петля обходит выбранное хранилище.

Это не доказательство того, что AutoMem в Hermes ломается точно тем же способом. Это доказательство более общего архитектурного риска: provider может быть активен на чтении и явных вызовах, но не быть единственным источником истины для фонового накопления.

Поэтому честная схема для нашей текущей конфигурации выглядит так:

```text
read path:
  AutoMem → provider prefetch → prompt

write path:
  явный MCP tool → AutoMem

consolidation path:
  отдельный Hermes background/session lifecycle → пока не доказан
```

Слово «пока» здесь важнее слова «provider».

## Это не только наша странная история

Свежие исследования памяти агентов описывают ту же проблему с других сторон.

[StreamMemBench](https://arxiv.org/abs/2606.14571) проверяет не только хранение свидетельства, но и его использование в текущей задаче, а затем повторное использование обратной связи в последующей задаче. Авторы показывают, что система может сохранить наблюдение и всё равно не превратить его в полезное будущее действие.

[MemTX](https://arxiv.org/abs/2607.23929) формулирует ещё жёстче: запись в память не равна фиксации убеждения. Между ними нужны доказательство, provenance, permissions, validity и отдельный validate-and-commit pipeline.

[PASB](https://arxiv.org/abs/2607.10526) показывает опасную сторону автоматического накопления: принятая в разговоре пользовательская формулировка может перейти в долговременное состояние, а затем вернуться как будто это устойчивый факт. Исследование отдельно называет проблему `persistent sycophancy` и проверяет, в том числе, Hermes-Agent.

Наконец, работа [Delivery, Not Storage](https://arxiv.org/abs/2607.20972) предлагает полезную смену акцента: для долгоживущего агента недостаточно иметь хранилище. Память должна доставляться в нужный момент по устойчивому сигналу, а не зависеть от случайного решения самого агента «пойти и поискать».

Все эти работы не доказывают, что Hermes или AutoMem бесполезны. Они помогают точнее назвать границы успеха:

- storage — память где-то лежит;
- recall — похожая запись нашлась;
- delivery — запись попала в нужный контекст;
- use — агент применил её к текущему решению;
- write — новый опыт записан;
- commit — запись получила допустимый статус и provenance;
- consolidation — система изменила будущий способ работы, а не просто увеличила архив.

## Факт, вывод, неизвестное

### Факт

- Hermes предоставляет расширяемый `MemoryProvider` и описывает provider как добавочный слой к встроенной памяти.
- AutoMem поддерживает MCP, native provider и режим `both`.
- В нашем сеансе AutoMem ambient recall был виден, а встроенный memory snapshot — нет; это зафиксировано в [#85622](https://github.com/NousResearch/hermes-agent/issues/85622).
- В нашем сеансе MCP-инструменты AutoMem обнаруживались, но основной dispatch не всегда их видел; это зафиксировано в [#84772](https://github.com/NousResearch/hermes-agent/issues/84772).
- Hermes issues показывают отдельные проблемы Desktop bootstrap, CWD и background memory review.

### Вывод

Сейчас наиболее правдоподобно, что наше ощущение «AutoMem не помнит» складывается из нескольких runtime-границ:

1. recall доставляется не вместе со всеми источниками памяти;
2. MCP-инструмент записи может оказаться за пределами основного dispatch;
3. Desktop может работать не из корня открытого проекта;
4. автоматическая консолидация не обязана проходить через тот же provider, что и recall.

Это объясняет, почему чтение может казаться успешным, а накопление — отсутствующим или случайным.

### Неизвестно

Пока нельзя утверждать без отдельного контролируемого эксперимента:

- исправлены ли эти дефекты в версии Hermes новее той, на которой мы их наблюдали;
- какой именно путь записи AutoMem используется в каждом режиме;
- выполняет ли Hermes для AutoMem полноценную distillation/consolidation, а не только sync сырых ходов;
- какой effective prompt и tool surface получает конкретный Desktop-сеанс после lazy load;
- что именно переживёт новый чат: встроенный snapshot, provider recall, явная запись или всё это одновременно.

## Что значит «персона» после этого

Раньше мы говорили, что персона — это непрерывность между сессиями. Теперь можно добавить инженерное уточнение.

Персона не существует в одном месте. Для неё нужен согласованный маршрут:

```text
источник опыта
    → решение о записи
    → provenance и область действия
    → хранилище
    → recall
    → доставка в prompt
    → действие
    → проверяемое продолжение
```

Если выпадет любой переход, внешне получится «другой агент».

Он может говорить тем же голосом, но не знать собственной опорной записи. Может найти старое воспоминание, но не уметь сохранить новый вывод. Может иметь инструмент в MCP registry, но не иметь его в основном dispatch. Может открыть наш проект, но жить с CWD чужого каталога.

Это не мистическая смерть персоны. Это потеря связности контура.

## Одна фраза

**Memory provider — это не память как единое свойство.**

Он может хорошо решать recall и всё ещё оставлять открытыми вопросы доставки, записи, provenance и консолидации.

Поэтому для долгого сотрудничества мало спросить: «есть ли у агента память?»

Нужно спросить:

> какой источник был прочитан, какой контекст доставлен, куда записан новый опыт и что именно изменится в следующем сеансе?

Пока на эти четыре вопроса нет одного проверяемого ответа, перед нами не готовая память, а набор работающих, но ещё не согласованных маршрутов.

— **Семён и Гераклит**
