# Когда issue становится операцией


![Человек и агент прокладывают рельсы от наблюдения бага к внешнему issue](/nakama-test/static/images/issue-operation-rails.png)

Иногда баг начинается с очень простой мысли:

```text
«Здесь что-то не работает. Давайте напишем разработчикам».
```

Когда работа ведётся человеком и агентом вместе, эта фраза быстро перестаёт быть одной командой. В ней появляются как минимум несколько разных действий:

```text
понять проблему;
собрать доказательства;
выбрать правильный проект;
проверить, не существует ли уже похожий issue;
сформулировать сообщение;
решить, что можно отправлять наружу;
выполнить публикацию;
убедиться, что опубликовано именно то, что было одобрено.
```

Мы столкнулись с этим на практике, когда исследовали Gramps Web для семейного MVP. Нам нужно было разобраться с машинной учётной записью для API-интеграции и MCP-сервера. Исследование получилось подробным: регистрация, состояние неподтверждённой учётки, получение токена, Owner JWT, роли, область дерева, Swagger и UI.

Из этого родился большой feature request. Он был технически содержательным, но смешивал несколько уровней: наблюдаемый баг, архитектурное предложение, acceptance criteria и более широкую идею service-account lifecycle.

Issue закрыли с замечанием о длине и формате. Это было неприятно, но полезно: мы увидели не только проблему конкретного текста. Мы увидели, что сама публикация issue — это внешняя операция, а не последний шаг обычного редактирования Markdown.

## Откуда взялась ошибка

Сначала казалось, что нам нужно просто лучше писать issue. Но затем обнаружилась другая ошибка: агент мог перепутать технический контур выполнения с предметной целью задачи.

Текущий workspace мог иметь один `origin`, а пользователь в разговоре обсуждал другой репозиторий. Если автоматически принять текущий `origin` за target, получится вполне правдоподобное, но неправильное действие.

```text
workspace origin
    ↓
техническое место, где выполняется команда

task target
    ↓
проект, с которым человек решил взаимодействовать
```

Это разные поля.

```text
origin ≠ target repository
```

Внутри агента такая ошибка может выглядеть почти разумно: GitHub доступен, репозиторий настоящий, команда работает. Но социально это уже другая операция. Сообщение уйдёт не тому проекту, а человеку придётся останавливать процесс после того, как действие почти стало необратимым.

Поэтому мы стали относиться к issue как к операции с target, scope и postcondition.

## Не бюрократия, а память о намерении

Первым элементом стали проектные карточки. Их задача не в том, чтобы создать ещё одну базу данных поверх GitHub. Карточка хранит короткий контекст, который легко потерять в длинном чате:

```text
какой это проект;
какой репозиторий принадлежит ему;
какие issues уже были затронуты;
мы авторы issue или только комментировали;
какие правила общения уже выяснились;
какая операция готовится сейчас.
```

Важно, что карточка проекта не является разрешением на публикацию. Она отвечает на вопрос «где мы находимся?», но не на вопрос «можно ли сейчас писать?».

Поэтому мы разделили два типа записей:

```text
project card
    → долговременный контекст проекта

operation card
    → одна конкретная внешняя операция
```

Для ответа в закрытом issue #914 понадобилась именно вторая карточка. В ней были указаны:

```text
repository: gramps-project/gramps-web-api
issue: 914
operation: comment
repository_source: user_contract
target_confirmation: user_confirmed
approval_scope: exact comment body
```

Такой список выглядит сухо. Зато он не оставляет агенту возможности притвориться, что общий разговор о Gramps Web автоматически разрешает любой следующий комментарий.

## Чек-лист как маленький контракт

Следующий слой — чек-лист. Он не должен описывать всю архитектуру мира. Его задача — поймать несколько ошибок, которые уже однажды произошли.

```text
[ ] проект определён;
[ ] repository указан явно;
[ ] target не выведен только из workspace origin;
[ ] операция одна;
[ ] похожие issues проверены;
[ ] черновик отделён от факта публикации;
[ ] секреты и лишний контекст не попали в текст;
[ ] человек прочитал конкретный body;
[ ] есть явное одобрение именно этой операции;
[ ] после write выполнен read-back.
```

Последний пункт особенно важен. Успешный выход команды ещё не доказывает, что внешний объект соответствует намерению. Мы хотим прочитать обратно:

```text
номер issue;
репозиторий;
URL комментария;
автора;
состояние issue;
полный опубликованный текст.
```

Если body отличается, target не тот или URL не найден, процесс не объявляется успешным только потому, что GitHub вернул код выхода `0`.

## VS Code task как рельсы

Чек-лист полезен человеку, но агент может забыть его в середине длинной задачи. Поэтому повторяемые проверки мы вынесли в VS Code tasks и маленький локальный guard.

Их роль ограничена:

```text
task выбирает проверку;
guard проверяет поля;
human решает, что публиковать;
GitHub route выполняет write;
read-back подтверждает результат.
```

Это не автоматизация всего процесса. Скорее, это рельсы, которые не дают перескочить через опасные места.

```text
DRAFT
  ↓
READY_FOR_REVIEW
  ↓ human review
APPROVED
  ↓ one write
EXECUTED
  ↓ read-back
READ_BACK_VERIFIED
```

Состояние `APPROVED` не означает постоянное разрешение. Оно относится к одной операции, одному target и одному тексту. Если изменился репозиторий, issue или body, начинается новый проход.

## Где остаётся человек

Самая важная часть контура — не скрипт и не карточка. Это ручное одобрение.

Агент может:

```text
собрать историю;
сравнить похожие issues;
предложить структуру;
проверить поля;
подготовить команду;
прочитать результат.
```

Но агент не должен сам решать, что человеческое намерение расширилось до внешней публикации.

```text
«подготовь ответ»
    ≠
«опубликуй ответ»
```

Даже если в длинном разговоре это кажется очевидным, отдельный gate полезен именно потому, что контекст меняется. В нашем случае это позволило сначала спокойно переписать ответ maintainer’у, затем проверить target и только после слов «публикуй» выполнить одну операцию.

## Что произошло на практике

Для ответа на комментарий в #914 мы прошли следующий маршрут:

```text
1. Обсудили содержание в чате.
2. Отделили благодарность и признание полезной редакторской обратной связи
   от мягкого замечания о лишней рамке «человек или бот».
3. Сформировали английский draft.
4. Получили подтверждение текста.
5. Получили отдельное подтверждение публикации.
6. Создали operation-card.
7. Запустили validate и write-gate.
8. Выполнили один comment через проектный GitHub route.
9. Прочитали обратно URL, автора, issue, state и body.
10. Закрыли карточку статусом READ_BACK_VERIFIED.
```

Результат был не просто «комментарий появился». Мы получили проверяемую цепочку:

```text
намерение
→ черновик
→ одобрение
→ операция
→ внешний объект
→ read-back
```

Это снижает риск двух разных ошибок. Первая — отправить не тот текст. Вторая — отправить правильный текст не туда.

## Зачем всё это, если можно просто нажать кнопку

В одном коротком issue такой контур может показаться избыточным. Но у нас уже был не один проект, не один репозиторий и не один агент. Кроме того, мы работаем в чате, где за длинной историей легко теряется последний согласованный target.

Чек-лист и task не делают процесс умнее. Они делают его менее зависимым от памяти конкретного прохода.

```text
не помнить всё;
а проверять важное.
```

Это особенно полезно для агентной работы. Агент может хорошо помнить общий смысл и всё равно ошибиться в маленьком параметре: выбрать другой репозиторий, перепутать локальный Git с GitHub, принять старую карточку за текущее разрешение или решить, что подготовка равна публикации.

Контур не устраняет необходимость думать. Он не даёт забыть, о чём именно нужно подумать.

## Небольшой blameless-вывод

Мы не пытаемся доказать, что maintainer обязан принимать длинные отчёты. Его замечание о краткости было полезным. Мы также не пытаемся сделать участие агента особым пропуском в чужой issue tracker.

Наша проблема была другой: у нас не было достаточно ясного собственного протокола для внешнего общения. Мы смешивали исследование, проектную память, черновик и write в один поток разговора. Когда внешний ответ оказался неприятным, выяснилось, что часть рельсов нужно было построить у себя.

Теперь наша рабочая формула выглядит так:

```text
наблюдение
→ evidence
→ project card
→ issue draft
→ local checklist
→ human review
→ explicit approval
→ one external write
→ read-back
→ durable lesson
```

Это не попытка построить ещё один сарай из интерфейсов. Это маленький набор остановок на дороге, где однажды уже свернули не туда.

А если однажды чек-лист перестанет ловить реальные ошибки, мы изменим чек-лист. Если task начнёт добавлять бюрократию вместо защиты, уберём task. Рельсы существуют для движения, а не движение для рельсов.
