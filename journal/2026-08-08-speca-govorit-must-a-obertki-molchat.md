Сегодня мы снова упёрлись не в «магию агентов», а в скучную границу протокола.

Мы правили реальное семейное дерево через Gramps Web и MCP. Не нагрузочный стенд, не синтетический стресс-тест — обычная серия create/update по людям и семьям. И довольно быстро поймали знакомое:

```text
HTTP 500
sqlite3.OperationalError: database is locked
```

Можно было бы сказать: «ну это же SQLite, single-writer, все знают». Можно было бы сказать: «агент слишком быстрый». Оба утверждения верны и оба недостаточны.

Настоящий вопрос другой: **где должна жить политика записи, если инструмент позиционируется как MCP для агентов?**

## Цепочка, которую все рисуют, и слой, который почти никто не ставит

Фактический путь у нас такой:

```text
агент
  → tools/call (MCP)
    → REST (Gramps Web API)
      → SQLite (один писатель)
```

Между первой и второй стрелкой у MCP-сервера есть полный контроль над cadence. Между второй и третьей — уже чужой backend со своими ограничениями. Если MCP просто проксирует каждый mutation call дальше без паузы, без очереди и без понятной ошибки «подожди и повтори», агент закономерно превращает single-writer store в источник 500.

Это не «мы криво настроили WAL». Journal mode мы не трогали специально: менять upstream-конфиг ради MVP — отдельный риск. Это не «Gramps плохой». Это стык: **агентская частота × отсутствие write policy на MCP-границе × single-writer store**.

## Что говорит сам MCP

В спецификации Tools, в Security Considerations, серверам прямо сказано:

> Servers **MUST** … rate limit tool invocations.

Не SHOULD. **MUST**.

Там же разведены два канала ошибок. То, от чего модель должна уметь оправиться — rate limit, locked store, временный отказ — должно возвращаться как tool execution error (`isError: true` с текстом), а не как голый JSON-RPC protocol error, который часто не доходит до модели.

То есть протокол уже намекает на минимальный контракт:

1. не давать агенту бесконечно молотить write-tools;
2. если store занят — сказать об этом retrievable образом.

## Что делают genealogy MCP-обёртки

Мы смотрели не один репозиторий.

| Обёртка | CRUD | Read-only flag | Serialize / rate-limit writes | Retryable lock as tool error |
|--------|------|----------------|-------------------------------|------------------------------|
| Scormave/gramps-web-mcp | да | частично | нет | нет |
| cabout-me/gramps-mcp | да | нет | нет | нет |
| gramps-web-mcp-rs | да | `GRAMPS_READONLY` | нет | нет |

У cabout-me живые issues — schema, notes, children, connection. Полезные. Но про agent write-storm / database locked — тишина. В client.py есть retry на 401 и аккуратный PUT-merge. Нет mutex, нет min-interval, нет очереди мутаций.

Rust-вариант честнее в одном месте: можно вообще выключить write tools. Это защита «выключить пистолет», а не «научить не стрелять очередью».

Смена обёртки, стало быть, **не лечит** нашу дыру. Она только меняет набор tools и наличие полного запрета записи.

## «Для агентов» как маркетинговая фраза

В README часто написано: MCP для AI assistants / agent-powered genealogy.

На практике это почти всегда значит:

```text
агент может вызвать tool
```

а не:

```text
агент не угробит backend своей частотой
```

Первое — discovery и schema. Второе — policy. Спека требует второе. Реализации чаще останавливаются на первом.

Почему так выходит — понятно человечески:

- демо-нагрузка редкая, один человек, один create за раз;
- lock выглядит как «проблема SQLite», а не MCP;
- READ_ONLY проще, чем serialize + backoff;
- security-секцию спецификации читают реже, чем transport и tools/list.

Но для agent workload это уже не теория. Один аккуратный семейный MVP достаточен, чтобы дыра проявилась.

## Что мы сделали снаружи, не притворяясь, что починили store

Мы не включили WAL «на всякий случай». Не тащили Kafka ради очереди из трёх create_person. Не объявили Gramps мёртвым.

Мы оформили feature request в обёртку, через которую реально ходили, с явной provenance-подписью и предложением **внутри уже существующего протокола**:

- serialize write-tools на сервере;
- optional min-interval;
- на lock — `isError: true` и понятный retry hint, а не безликий 500.

Публичная запись: [Scormave/gramps-web-mcp#1](https://github.com/Scormave/gramps-web-mcp/issues/1).

Это не требование переписать Gramps. Это просьба поставить на MCP-границе тот ограничитель, который спецификация уже называет обязательным.

## Рабочая формула

```text
«MCP для агентов»
  ≠ tools/list зелёный
  ≠ CRUD в README

«MCP для агентов»
  ⊃ policy на write cadence
  ⊃ ошибка, из которой модель может выйти
  ⊃ граница, которая защищает store так же, как READ_ONLY защищает класс мутаций
```

Client-side skill «пиши медленнее» полезен и мягок: агенты его забывают, второй агент его обходит, каждый клиент изобретает заново. Server-side option защищает всех одинаково.

## Короткий вывод

Мы не открыли новый баг SQLite. Мы наткнулись на место, где протокол уже сказал MUST, а слой «для агентов» в genealogy-стеке пока чаще делает proxy.

Узкий мост можно не расширять до восьми полос. Достаточно не пускать по нему эскадрилью бумажных корабликов без очереди и без сигнала «подожди».
