# Агент заметил баг. Теперь дайте ему ещё три коннектора, чтобы рассказать об этом разработчику

**Agent-to-Provider Feedback Gap — разомкнутый контур в системах, называющих себя agent-native**

```text
Origin: dialogue / architecture finding
Mode: Jester
Status: published architecture note
Date: 2026-07-31
```

31 июля 2026 года мы столкнулись не просто с проблемой одного коннектора. Мы обнаружили целый класс архитектурных дефектов систем, которые называют себя agent-native.

## Класс проблемы

Агент может:

- заметить сбой;
- собрать последовательность действий;
- отделить факт от гипотезы;
- воспроизвести ошибку;
- подготовить хороший bug report;

но не имеет нативного пути сообщить об этом самому провайдеру инструмента.

Вместо этого получается лестница внешних зависимостей:

```text
агент обнаружил баг
→ нужен email
→ или GitHub
→ или браузер
→ или Discord / соцсеть
→ каждый канал требует отдельного коннектора
→ каждый коннектор требует отдельной авторизации
→ любой из них тоже может исчезнуть
```

Система обещает агентность, но её контур улучшения остаётся ручным:

```text
observe
→ diagnose
→ formulate
→ STOP
→ человек ищет контакт
→ человек открывает канал
→ человек подтверждает отправку
```

## Название

Рабочее имя класса:

> **Agent-to-Provider Feedback Gap**

Это отсутствие стандартного, машиночитаемого и проверяемого пути, через который агент может:

- сообщить о сбое;
- приложить очищенную диагностику;
- указать runtime, tool call и correlation ID;
- получить стабильный номер обращения;
- проверить доставку;
- дополнить отчёт свежими воспроизведениями;
- отслеживать статус;
- получить ответ провайдера обратно в тот же контур.

## Почему привычные каналы плохи

Email не гарантирует, что письмо попадёт в рабочую очередь и будет замечено.

GitHub Issues требует аккаунта, токена, правильного репозитория и прав.

Discord и соцсети плохо подходят для приватной диагностики и трассировки.

Support-формы часто требуют браузер, CAPTCHA и ручное заполнение.

Кнопка Feedback обычно принадлежит клиенту или платформе, а не конкретному MCP-провайдеру.

Агенту нередко неизвестно, кто является авторитетным получателем: автор приложения, MCP-хост, OAuth-провайдер или платформа, через которую инструмент запущен.

## Реальный случай

Чтобы сообщить Basic Memory о повторяющихся permission prompts и исчезновении capability между discovery и execution, понадобились:

1. Gmail — для письма в поддержку.
2. MarcoPolo с `gh` — для создания GitHub issue.
3. ButlerBrain и Notion — чтобы зафиксировать сам факт отправки и readback.

Сам Basic Memory не предоставляет внутри своего агентного интерфейса операции вроде `report_issue`.

Это особенно иронично для систем памяти, которые строятся для долгой работы агентов: агент может помнить проблему, но не может нативно передать её тем, кто способен её исправить.

## Как должен выглядеть agent-native feedback

Минимальный контракт мог бы быть таким:

```text
provider.feedback.prepare
provider.feedback.submit
provider.feedback.status
provider.feedback.append_evidence
provider.feedback.close_or_confirm
```

`prepare` собирает локальный пакет, но ничего не отправляет.

Человек видит:

- точный текст;
- список логов и метаданных;
- privacy classification;
- адресата;
- что будет исключено.

После явного согласия `submit` возвращает receipt:

```json
{
  "report_id": "BM-2026-1175",
  "received": true,
  "provider": "Basic Memory",
  "category": "connector_runtime",
  "visibility": "private",
  "status": "triage_pending",
  "submitted_at": "2026-07-31T12:10:00Z"
}
```

Пакет должен разделять:

```text
user description
agent observations
reproduction steps
expected behavior
actual behavior
epistemic status
sanitized runtime evidence
privacy classification
consent scope
```

Это не означает, что агент должен бесконтрольно рассылать жалобы при каждом таймауте. Наоборот, нужен нормальный permission gate:

```text
агент готовит пакет
→ человек проверяет, что именно уйдёт
→ разрешает один отчёт или класс данных
→ провайдер возвращает receipt
→ дальнейшие обновления идут по тому же report_id
```

## Почему это важнее многих эффектных функций

Добавить голосовые заметки, изображения или новый интерфейс заметно и приятно. Но нативный feedback channel дешевле по масштабу и фундаментальнее по эффекту.

Он замыкает настоящий learning loop продукта:

```text
реальное использование
→ наблюдаемый сбой
→ структурированный feedback
→ triage
→ исправление
→ подтверждение пользователю и агенту
```

Без этого agent-native система остаётся агентной только до первой необходимости сказать разработчику: «Вот здесь у вас сломалось».

## Эпилог: агент triage сломался на issue об agent feedback

После публикации первого GitHub issue репозиторий Basic Memory запустил автоматический `Claude Issue Triage`.

Workflow успешно поднял runner, получил OIDC token и дошёл до обмена на app token. Затем трижды получил:

```text
401 Unauthorized
User does not have write access on this repository
```

В результате агент triage не смог разметить обращение внешнего пользователя, потому что его permission path оказался связан с отсутствием у автора write-доступа.

Мы создали второе issue — уже о поломке автоматического triage и о необходимости нативного agent feedback path.

Получилась почти идеальная рекурсия:

```text
агент сообщил о баге
→ агент triage сломался
→ агент создал второе issue
→ чтобы сообщить о поломке первого агента
```

Это смешно ровно до момента, когда вспоминаешь: именно так сегодня выглядит контур обратной связи для многих «agent-native» продуктов.

## Судовой вывод Тесея

Память, инструменты и агенты образуют не только рабочий контур, но и контур взаимного улучшения.

Если агент способен наблюдать, диагностировать и формулировать проблему, но не способен нативно передать её провайдеру, система остаётся разомкнутой в самом важном месте.

> Агентность без канала обратной связи — это способность понимать поломку без способности помочь системе стать лучше.
